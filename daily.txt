  3. 最复杂的技术难点：JWT 无状态认证体系的完整实现

  这是项目中技术含量最高的部分，你不是仅仅"用了
  JWT"，而是从零搭建了一套完整的认证过滤链。

  难点在于：
  Spring Security 的默认机制是基于 Session 的有状态认证，但 REST API
  需要无状态的 JWT 认证。这两者需要整合，否则每个请求都会被 Security 拦截。

  你的解决方案（从代码推断）：

  1. JwtUtil.java — 封装 JWT 的签发与解析逻辑
    - 使用 HS256 算法 + 32字符以上密钥
    - Token 有效期设为 7 天
    - Payload 中嵌入 userId 和 username
  2. JwtAuthenticationFilter.java — 自定义过滤器（OncePerRequestFilter）
    - 从每个请求的 Authorization: Bearer <token> 头中提取 token
    - 解析成功后，手动将用户信息注入 Spring Security 上下文
  (SecurityContextHolder)
    - 对 token 过期/解析失败做了优雅处理（不抛异常，而是放行到后续鉴权失败）
  3. SecurityConfig.java — 将自定义 Filter 注册到 Security 过滤链
    - 禁用 CSRF（REST API 无需）
    - 白名单放行 /api/auth/**（登录注册不需要 token）
    - 将 JwtAuthenticationFilter 置于 UsernamePasswordAuthenticationFilter 之前

  这个三层联动的设计，是很多初学者做不到的地方。

  ---
  索引原理：为什么这么设计

  改前 vs 改后的执行路径

  改前，执行 WHERE user_id=1 AND is_delete=0 AND date BETWEEN '03-01' AND 
  '03-30'：

  idx_userid(user_id)
    → 找到 user_id=1 的所有行（假设100条）
    → 回表读取每一行，逐条检查 is_delete 和 date
    → 扫描100行，过滤出20条

  改后，执行同样的查询：

  idx_bill_user_delete_date(user_id, is_delete, date)
    → user_id=1 AND is_delete=0 → 锁定B-Tree的一个区间（已过滤掉软删除数据）
    → date BETWEEN ... → 在这个区间内做范围扫描
    → 直接得到目标行，大幅减少扫描量

  ---
  为什么列顺序是 user_id → is_delete → date，不能乱

  B-Tree 索引的最左前缀原则：

  索引 (user_id, is_delete, date)

  能命中索引的查询：
    WHERE user_id=1                              ✓ 用到第1列
    WHERE user_id=1 AND is_delete=0              ✓ 用到前2列
    WHERE user_id=1 AND is_delete=0 AND date=?   ✓ 用到全部3列
    WHERE user_id=1 AND is_delete=0 AND date BETWEEN ? AND ?  ✓ 范围查询在最后

  命不中的查询：
    WHERE is_delete=0 AND date=?                 ✗ 缺少最左列 user_id
    WHERE user_id=1 AND date=?                   ✗ 跳过了 is_delete（中间断了）

  范围条件必须放最后，是因为 B-Tree 一旦遇到范围（BETWEEN/>/<），后面的列就无法
  继续走索引定位，只能在范围内顺序扫描。

  ---
  为什么 todo 要两个索引，bill 只要一个

  bill 的查询：几乎都带 date 条件（记账按日期查）
    → 一个 (user_id, is_delete, date) 覆盖全部

  todo 的查询：分两种高频场景
    → 首页"今日待办"：WHERE user_id=? AND is_delete=0 AND date=?
      命中 idx_todo_user_delete_date ✓
    → 首页"未完成数量"：WHERE user_id=? AND is_delete=0 AND status=0
      date 索引帮不上忙，需要 idx_todo_user_delete_status ✓

  ---
  为什么可以删掉原来的 idx_userid

  复合索引 (user_id, is_delete, date) 的最左列就是
  user_id，所以它完全覆盖了原来单列 idx_userid(user_id)
  的功能。两个索引共存只会浪费空间、拖慢写入速度，删掉更合理。

  ▎ 注意： idx_userid 原本还承担 MySQL 外键约束的索引支撑。MySQL 
  规定外键列必须有索引，但复合索引只要以该列开头就满足条件，所以删掉 idx_userid 
  后，外键约束依然由复合索引支撑，不会报错。

  ---
  如果已有数据库在运行，如何应用这个变更

  SQL 文件用于重建数据库。如果是对已有的生产库打补丁，对应的命令是：

  -- 对已有数据库直接执行
  ALTER TABLE bill
      DROP INDEX idx_userid,

  ---
  @Transactional 原理：为什么批量操作必须加

  没加之前，出错会发生什么

  以 batchDelete 为例，它做了两步数据库操作：

  // 第一步：查出所有记录
  List<Bill> list = billRepository.findAllById(ids);  // SELECT

  // 修改内存中的标记
  for (Bill bill : list) { bill.setIsDelete(1); }

  // 第二步：批量写回
  billRepository.saveAll(list);  // 多条 UPDATE

  saveAll 底层对 list 里每一条记录分别执行一条 
  UPDATE。如果处理到第5条时数据库连接断了，或者触发了某个约束异常：

  UPDATE bill SET is_delete=1 WHERE id=1  ✓ 已提交
  UPDATE bill SET is_delete=1 WHERE id=2  ✓ 已提交
  UPDATE bill SET is_delete=1 WHERE id=3  ✓ 已提交
  UPDATE bill SET is_delete=1 WHERE id=4  ✓ 已提交
  UPDATE bill SET is_delete=1 WHERE id=5  ✗ 异常！

  结果：1-4 被删了，5 没删，数据状态不一致。

  加了 @Transactional 之后：

  整个方法 = 一个事务

  UPDATE id=1  ─┐
  UPDATE id=2   │  全部在同一个事务里
  UPDATE id=3   │
  UPDATE id=4   │
  UPDATE id=5  ─┘

  → 全成功：一次性 COMMIT
  → 任意一条失败：全部 ROLLBACK，数据回到调用前的状态

  ---
  Spring 的事务传播机制（面试高频）

  @Transactional 默认传播行为是 PROPAGATION_REQUIRED，意思是：

  调用方没有事务 → 新建一个事务
  调用方已有事务 → 加入已有事务（不新建）

  对这个项目意味着：将来如果某个 Service 方法调用了
  batchDelete，它们会共享同一个事务——任何一个失败，整体回滚。

  ---
  为什么用 org.springframework.transaction.annotation.Transactional 而不是 
  jakarta.transaction.Transactional

  Java 里有两个同名注解：

  ┌───────────────────────────────────────┬──────┬─────────────────────────┐
  │                 注解                  │ 来源 │        适用场景         │
  ├───────────────────────────────────────┼──────┼─────────────────────────┤
  │                                       │      │ Spring 项目首选，功能更 │
  │ org.springframework.transaction.annot │ Spri │ 丰富（可配置            │
  │ ation.Transactional                   │ ng   │ rollbackFor、propagatio │
  │                                       │      │ n、isolation 等）       │
  ├───────────────────────────────────────┼──────┼─────────────────────────┤
  │                                       │ Jaka │ JEE 规范，Spring        │
  │ jakarta.transaction.Transactional     │ rta  │ 也能识别，但功能子集    │
  │                                       │ EE   │                         │
  └───────────────────────────────────────┴──────┴─────────────────────────┘

  Spring 项目统一用 Spring 自己的，避免功能受限。

  ---
  一个值得知道的细节：@Transactional 的回滚规则

  Spring 默认只对 RuntimeException 和 Error 回滚，受检异常（checked 
  exception）不回滚。

  @Transactional
  public void batchDelete(List<Long> ids) {
      // 如果这里抛出 IOException（checked）→ 不会回滚！
      // 如果抛出 RuntimeException  → 回滚 ✓
  }

  如果方法里有可能抛受检异常，需要显式指定：
  @Transactional(rollbackFor = Exception.class)  // 所有异常都回滚

  当前项目的批量操作不涉及受检异常，默认行为已经够用，不需要额外配置。

● 全部改完。下面把每一个设计决定讲清楚。

  ---
  设计解析

  整体改动路径

  请求：GET /api/bill/list?page=0&size=10
                             ↓
  Controller：PageRequest.of(0, 10, Sort.by(DESC, "date", "id"))
                             ↓
  Service：billRepository.findByUserIdAndIsDelete(userId, 0, pageable)
                             ↓
  Repository：Spring Data 自动生成带 LIMIT/OFFSET 的 SQL
                             ↓
  返回：Page<Bill>（含分页元数据）

  ---
  为什么 Repository 只加一行就够了

  // 原有：
  List<Bill> findByUserIdAndIsDelete(Long userId, Integer isDelete);

  // 新增：多一个 Pageable 参数，Spring Data 识别并生成分页 SQL
  Page<Bill> findByUserIdAndIsDelete(Long userId, Integer isDelete, Pageable 
  pageable);

  Spring Data JPA 的方法名解析机制会把 Pageable 参数识别为分页指令，自动在 SQL
  里加 LIMIT ? OFFSET ?，并额外执行一条 SELECT COUNT(*) 来计算总数——这两条 SQL
  都是框架自动生成的，不需要手写。

  ---
  PageRequest.of(page, size, Sort...) 的三个参数

  PageRequest.of(
      page,                                            // 页码，从 0 开始
      size,                                            // 每页条数
      Sort.by(Sort.Direction.DESC, "date", "id")       // 
  排序：先按日期倒序，同日期再按 id 倒序
  )

  排序加 id 作为第二排序键是为了保证稳定性：同一天的多条记录在不同页之间顺序固定
  ，否则分页边界可能出现重复或漏条。

  ---
  接口响应结构（Page<T> 序列化结果）

  GET /api/bill/list?page=0&size=10

  {
    "content": [ {...}, {...}, ... ],   ← 当前页数据
    "totalElements": 47,                ← 总记录数
    "totalPages": 5,                    ← 总页数
    "number": 0,                        ← 当前页码（从0开始）
    "size": 10,                         ← 每页大小
    "first": true,                      ← 是否第一页
    "last": false                       ← 是否最后一页
  }

  GET /api/bill/list?page=0&size=10&date=2026-03-30   ← 按日期查，不分页
  [ {...}, {...} ]                                      ← 直接返回数组

  ---
  为什么用 Object 做返回类型，而不是 Page<Bill>

  // 这样写，两种场景返回类型不同（List vs Page），编译器会报错
  public List<Bill> getBillList(...) { ... }

  // 用 Object，让 Jackson 序列化器在运行时决定具体类型
  public Object getBillList(...) { ... }

  同时保持了向后兼容：原来前端不传 page
  参数，接口依然返回数组，不会因为加了分页功能就把旧调用搞坏。

  ---
  面试时怎么说

  ▎ "我用 Spring Data JPA 的 Pageable 机制实现了分页。Repository 
  层只需要在方法签名里加 Pageable 参数，框架自动生成带 LIMIT/OFFSET 的 SQL 和 
  COUNT 查询。

  ▎ Controller 接收 page 和 size 参数，构造 PageRequest 
  时加了双字段排序（先按日期、再按 id），保证分页结果稳定不重复。返回 Page<T> 
  对象，前端能直接拿到 totalPages、totalElements 等元数据，不需要额外接口。

  ▎ 同时保留了不传 page 时返回全量的逻辑，向后兼容已有调用。"
